## 02. Dashboard and connection state

## 03. Create a closed geofence

The geofence form collects a name, an optional description, one of four categories, and a polygon. The categories follow the assessment vocabulary exactly: delivery zone, restricted zone, toll zone, and customer area. The API uses their underscore separated identifiers. The map supports drawing by clicking vertices, undoing the most recent vertex, clearing the draft, and closing the polygon.
Closing is an explicit step because the request contract requires the final coordinate to equal the first. A triangle therefore needs four coordinate pairs: three different vertices and one repeated closing point. The form also accepts a JSON array, which is useful for reproducing a known shape precisely. Both methods use latitude followed by longitude. The backend validates the submitted shape even if it was created through the map.
The example is a local rectangle in San Francisco. It is deliberately small enough for planar point containment. The implementation does not claim to support polygons spanning the antimeridian or the poles. The saved polygon is rendered on the map, and the directory shows its category and description. Category filtering affects which saved boundaries are visible in that view.

## 04. Validation before saving

Geofence validation is implemented on the server, not delegated to the browser. The function rejects an empty name and unknown categories. It checks the number of points, every coordinate pair, latitude and longitude ranges, explicit closure, and at least three distinct non collinear points. It also checks for self intersections between non adjacent edges. A maximum point count bounds the cost of that quadratic validation pass.
These checks prevent several common mistakes. A list of unrelated coordinates is not a polygon. An open ring violates the documented contract. Repeating the same coordinate four times satisfies a naive length check but does not enclose an area. A bow tie may have four apparent corners, but its edges cross and create an ambiguous interior.
The response for invalid input is a clear client error containing an error message and execution time. The frontend displays that message instead of silently accepting an invalid fence. Browser validation improves convenience, but the API remains the authority because any client can submit JSON directly. The geometry tests include invalid polygons, interior points, exterior points, edges, and vertices so that boundary behavior is a deliberate decision rather than an accident.

## 05. Register and inspect vehicles

The vehicle registration form requires a registration number, driver name, vehicle type, and phone value. These are demonstration values in the recording. Real driver details should only be used after access control and privacy requirements are addressed. A vehicle number is unique in the database, so registering the same number twice returns a conflict rather than creating indistinguishable fleet records.
Registration does not invent a starting location. Until an actual location update arrives, the vehicle status reads awaiting location. That is more honest than placing a new vehicle at a default map center. When a location is known, the list shows the current geofences containing that position, or outside zones if there are none.
A vehicle can be inside more than one fence at the same time. The response therefore uses a list of current geofences rather than a single zone field. This is important for overlapping operational areas, such as a customer area inside a delivery zone. The application preserves the distinction between a registered vehicle, its latest observation, and the set of polygons currently containing that observation. The next step configures which transitions should become real time notifications.

## 06. Configure matching alert rules

An alert rule connects a geofence to an event type and optionally a vehicle. Omitting the vehicle means the rule applies to all vehicles. Choosing one vehicle narrows it to that vehicle identifier. Event type can be entry, exit, or both. The API validates that the fence exists and, when provided, that the vehicle exists before storing an active rule.
Rules do not themselves move a vehicle or manufacture a transition. They determine whether an observed membership change should be delivered to connected clients. All detected transitions are recorded in event history even when no rule matches. This allows the history to remain useful for auditing while keeping the live alert feed focused on configured monitoring needs.
The implementation checks all rules for a given transition and treats matching as a boolean. As a result, a general rule and a vehicle specific rule can both match without producing duplicate notifications for the same crossing. This is a deliberate simplification: a future system might notify different recipients for different rules, but this application broadcasts one event to the dashboard clients. Rule creation and listing are implemented; editing and deleting existing rules are listed as follow up work.

## 07. Send location observations

The location update form allows coordinates to be entered manually or chosen on the map. The timestamp represents when the observation was recorded. It is sent to the server in an explicit time zone format. The vehicle must already be registered. A successful response reports that the location was updated and returns every geofence containing the new point.
The backend requires both latitude and longitude. Pointer fields distinguish a missing numeric field from zero, because zero is a valid coordinate. Range checks reject impossible latitude and longitude values. The timestamp must parse successfully, and it must be newer than the latest stored observation for that vehicle. Older and equal timestamps return a conflict.
Rejecting stale observations keeps a delayed network packet from rewinding the current state. This simple policy suits the assessment, although a production tracking platform could preserve late observations in a separate historical path while keeping the live state monotonic. Here, accepted updates are appended to the locations table. The containment comparison and event creation happen in the same ordered request flow so that two simultaneous updates cannot both compare against an inconsistent previous state.

## 08. Observe entry and exit alerts

An entry is a change from outside a fence to inside it. An exit is the reverse. Merely receiving another update while a vehicle remains inside does not create another entry. The first observation has no previous position. This implementation treats an initial observation inside a fence as an entry from an unknown outside baseline, and documents that choice.
A matching alert includes an event identifier, event type, timestamp, vehicle information, geofence information, and the reported coordinates. The live feed displays these fields so that an operator can tell which vehicle crossed which boundary. The category gives context, especially for restricted zones.
The demonstration sequence starts outside, moves inside, remains inside, and then moves outside. There should be exactly two transitions for that fence. The backend integration test also opens two independent WebSocket clients and checks that both receive the same entry followed by the same exit. That verifies delivery to multiple consumers rather than only confirming a single browser receives something. An automated test cannot replace deployment testing, but it establishes the expected behavior of the running server before external hosting is introduced.

## 09. Persistent history and filters

The event history view reads stored transitions from the backend. It supports filtering by vehicle, geofence, a starting date, and an ending date. The date range is inclusive. The API also accepts a page size and an offset. The dashboard requests ten records at a time and uses the total matching count to decide whether another page is available.
The total count is computed before pagination. Otherwise a page with ten records would misleadingly report that only ten events exist. Limits are bounded, and invalid dates or negative offsets produce client errors rather than silently changing the query. Empty results have an explicit empty state.
This implementation filters history records in Go after reading stored event JSON. That is correct for a small assessment dataset, but it is a documented scaling limitation. The database includes indexes, yet these indexes cannot accelerate filters that are applied only after all rows have been read. An improvement would move structured fields and date comparisons into parameterized SQL and use an indexed cursor for pagination. The current design prioritizes a small, understandable implementation while preserving the required API shape and clear behavior.

## 10. Docker execution and reproducibility

The application is packaged as two container images. The backend image uses a multi stage build: Go compiles the executable in a build stage, and a smaller runtime image contains the executable and certificate support. The runtime uses a non root user. SQLite data is stored under a dedicated data directory rather than inside the application image.
The frontend image builds the React application with Node and serves the resulting static files with Nginx. The API base URL is a build argument. That distinction is important: changing a container environment variable after the static JavaScript has been built does not rewrite the value inside the bundle.
Compose connects the two services through published local ports and a persistent named volume for the local database. A health check waits for the backend before the frontend starts. The local runtime check starts both containers, calls the health endpoint, loads the frontend, creates demo records, and restarts the backend to verify that the records remain. Docker configuration validation is also part of automated verification. Image publication to Docker Hub is a separate authenticated action; building an image locally does not by itself produce a public registry link.

## 11. Project structure and request flow

The source is divided into backend, frontend, scripts, and deployment documentation. The Go application keeps route handling, validation, containment, and event delivery in the backend. A separate database adapter selects SQLite or PostgreSQL while allowing the same repository owned parameterized queries to be used. The React source manages forms, map layers, the live stream, and history filtering.
A useful way to understand the system is to trace one location request. The browser submits JSON. The handler validates the vehicle, coordinates, and timestamp. It retrieves the latest observation and saved fences. It compares old and new membership, checks alert rules, and writes the location and transition records in a database transaction. Only after a successful commit are matching messages offered to connected clients.
The HTTP response returns the current containment state and execution time. Meanwhile, each WebSocket connection writes messages independently from its buffered channel. This separates the request's database work from slow network writes. The design is intentionally single instance: one application mutex orders REST operations. That is straightforward to reason about, but it is not presented as a high throughput distributed architecture.

## 12. Exact API contracts and timing

The route names follow the assignment contract. Geofences and vehicles each have create and list operations. Location updates use the documented vehicle location route, and current location is retrieved using the vehicle identifier in the path. Rules are configured and listed under the alert routes. Historical transitions are returned under the violations history route.
Every JSON API response adds execution time as a string named time underscore n s. The timing starts at handler entry and is measured when the response is constructed. Error paths use the same response helper, which means validation failures and missing resources also include the timing field. WebSocket frames use their documented event payload rather than being ordinary JSON HTTP responses.
The decoder limits request body size, rejects unknown fields, and requires one JSON value. That avoids accepting trailing unrelated JSON or accidentally ignoring misspelled request fields. Database failures return a general server error to the client while details are logged. A production system would add structured error codes, correlation identifiers, observability, and carefully bounded request execution time. The current contract stays simple while remaining explicit enough for tests and the dashboard to consume consistently.

## 13. Point containment and boundaries

The containment function uses a ray casting method. Imagine a ray extending from the point across the polygon. Each time a polygon edge crosses that ray, the inside flag toggles. An odd number of crossings means the point is inside; an even number means it is outside. The implementation iterates over consecutive vertices in a closed ring.
Before applying the crossing rule, it checks whether the point lies on an edge. Boundary points count as inside. This avoids an implicit and inconsistent boundary policy. A vehicle moving onto a boundary from outside can therefore create an entry, while movement along the boundary does not repeatedly change membership.
The coordinates remain in latitude, longitude order throughout this implementation. Leaflet accepts that order, so no reversal is needed in the map layer. If the geometry were moved into GeoJSON or PostGIS geometry constructors, the coordinate convention would need to be adapted to longitude followed by latitude. This is a frequent source of apparently valid but geographically misplaced shapes. The current approach is planar and intended for local regions. Global or highly precise geospatial requirements would justify a spatial database and carefully defined spherical geometry semantics.

## 14. Geometry validation edge cases

The geometry helpers use cross products to reason about orientation and whether a point lies on a segment. Two non adjacent polygon edges should not intersect in a simple ring. Adjacent edges are allowed to meet at their shared vertex, and the first and last edge meet at the closing point. The validator deliberately excludes those expected adjacent contacts from the self intersection rejection.
Floating point comparisons require tolerance. The on segment check uses a small tolerance around the cross product and bounding ranges. This improves stability near an edge, but the tolerance is a numerical choice rather than a universal geographic accuracy guarantee. Degrees are not a constant distance in meters, especially across latitudes.
The test cases include an ordinary square, interior and exterior observations, points on edges, and vertices. Invalid examples include unclosed shapes, collinear vertices, and crossing edges. More comprehensive property tests could compare randomly generated simple polygons against a trusted geometry library. A production implementation should also decide how to handle holes, multi polygons, very large coordinate ranges, and geometry changes while vehicles are already inside. These capabilities are outside the submitted shape model and should not be inferred from the simple polygon interface.

## 15. Atomic location and event storage

The location handler opens a transaction after validation and reads needed for the transition comparison. The location observation is inserted, and each membership change produces a history record. Matching alert payloads are stored alongside the event. If an insert or commit fails, the operation does not publish those prepared messages as if the data had been accepted.
The application mutex orders the whole REST request flow. With a single process, another location update cannot interleave between the previous state comparison and the transaction commit. This prevents duplicate or contradictory transitions caused by two goroutines using the same old state. The database connection pool is also restricted in this compact implementation.
There is an important limit: the mutex protects only one process. Starting two application instances would require database level locking or another ordering mechanism per vehicle. The transaction also does not guarantee eventual live delivery after a process crash. A crash after commit but before broadcast leaves a valid historical event without a live message. The stored event is still queryable, but guaranteed delivery would require an outbox dispatcher, acknowledgments, retries, and idempotent consumers. The roadmap returns to that distinction later.

## 16. Rule matching and deduplication

After detecting a transition, the handler checks saved rules. A rule must name the same fence. Its vehicle must either be omitted or match the vehicle being updated. Its event type must match the transition or be both. Only then is the transition eligible for live delivery.
The code produces one event identifier for the transition before checking all matching rules. Matching is represented by a boolean, so overlapping rules do not create multiple copies of the same event in the broadcast feed. The history record and the live message share that event identifier, making it possible to relate the notification to the stored transition.
A richer notification system would treat rules as policies with recipients, channels, priorities, suppression windows, and enable or disable state. In that design, deduplication would need to consider the destination and policy semantics rather than collapsing every match. For the assessment, a single dashboard broadcast is sufficient and easier to verify. Restricted zones are not hard coded to generate notifications without a rule; they use the same explicit configuration mechanism. Operators should configure the desired rule before expecting alerts from a particular zone.

## 17. WebSocket lifecycle and backpressure

Each WebSocket connection gets a bounded message channel. The server registers that channel in a client map protected by a separate mutex. A reader goroutine listens for connection failure and processes protocol control frames. The writing loop sends queued application messages and periodic pings, with deadlines to prevent an unresponsive client from blocking forever.
When the API publishes an event, it offers the serialized payload to each client channel without waiting for network transmission. If a channel is full, that slow client is removed and its channel is closed. The connection loop then ends. This is a deliberate backpressure policy: one slow browser must not slow vehicle location requests for every other user.
The browser reconnects after a connection closes. Reconnection restores future live messages; it does not automatically replay everything missed during the gap. Historical events remain available through the history endpoint. For stronger recovery, a future version could accept a last seen event cursor and replay stored alerts before switching to the live stream. At larger scale, the client registry would also need to be distributed across application instances through a broker or dedicated real time gateway.

## 18. SQLite and PostgreSQL storage

Local development uses an embedded SQLite database. Its schema is created on startup, with foreign keys enabled, write ahead logging, and a busy timeout. Vehicle numbers have a unique constraint. Locations are append only and have an index for retrieving the latest observation by vehicle. Event tables preserve history and matching alert payloads.
For a hosting environment with an ephemeral local filesystem, the application can instead read a PostgreSQL connection URL. The adapter selects the PostgreSQL driver, creates the equivalent schema, and translates placeholder syntax for repository owned queries. SQLite question mark placeholders become numbered PostgreSQL parameters. Ordering by SQLite row identifier is mapped to an explicit sequence column in PostgreSQL.
The adapter is intentionally narrow. It is not a general SQL parser and must not be used to transform arbitrary user supplied SQL. All current queries are defined in the source, and request values remain separate parameters. PostgreSQL support provides remote relational persistence; it does not automatically add PostGIS, a spatial index, multiple instance safety, or SQL side history optimization. Those remain separate architectural changes that should be evaluated rather than assumed.

## 19. React state and map integration

The frontend keeps saved fences, vehicles, rules, current positions, and the live feed in React state. An API helper sends JSON and turns non successful responses into user visible errors. Refresh loads the three main lists and then requests current location information for each registered vehicle.
Leaflet owns its map instance through a ref. The map is initialized once, and a layer group is rebuilt when relevant state changes. Saved fences become polygons, known vehicle locations become markers, and a drawing draft becomes a line. Text tooltips are created as text nodes rather than concatenated HTML, avoiding a simple route for names to become injected markup.
Map click handling reads the current mode from a ref. In draw mode, clicks append vertices. In move mode, they choose a location point. In inspection mode, clicks do not mutate the draft. This separates map interaction from form submission, allowing the user to inspect the chosen coordinates before sending them. The component is intentionally compact. As the application grows, extracting API hooks, map controls, forms, and history into separate modules would make independent testing and maintenance easier.

## 20. Frontend reconnect and feedback

The real time effect creates a WebSocket URL from the configured API base URL. HTTPS becomes secure WebSocket automatically. On connection open, the dashboard marks the live state active. Incoming messages are parsed and prepended to the feed, capped to a bounded number of recent items in memory. The notification includes the vehicle, transition, and geofence.
When the connection fails, it closes and schedules another attempt. Cleanup prevents a disconnected component from starting another reconnect loop. This keeps the basic lifecycle understandable, although a production client should add exponential backoff with jitter to avoid synchronized reconnect storms after a service restart.
Forms disable their action buttons while a mutation is in progress and display success or error feedback. Date and coordinate inputs give immediate browser assistance, while backend validation still remains authoritative. The current implementation refreshes data after actions and matching alerts, and polls fleet information periodically. That polling can create many requests as the fleet grows because current locations are loaded per vehicle. A combined fleet snapshot endpoint, conditional requests, or a dedicated position stream would reduce that cost. These tradeoffs are discussed openly rather than presenting every state refresh as an optimized real time pipeline.

## 21. Integration and race tests

The integration test starts the real application handler behind a test HTTP server and uses a temporary database. It creates a fence, registers a vehicle, checks duplicate registration, configures rules, and calls the list and current location endpoints. Requests verify both the expected status code and the timing field.
Two WebSocket clients connect independently. The test sends outside, inside, still inside, and outside observations. Both clients must receive entry followed by exit. A general rule and a vehicle specific rule are both present, so the test also checks that multiple matching rules do not multiply messages. Missing coordinates and stale timestamps are rejected.
The test then verifies pagination and reopens the database to check persistence. PostgreSQL can run the same workflow against an isolated temporary schema when its test connection URL is provided. The schema is generated for the test and removed afterward. Running the Go race detector adds checks for unsafe concurrent access during the exercised paths. Passing these checks is useful evidence, but it does not prove behavior for every possible scheduling interleaving, network failure, or load level. Load testing and longer reconnect tests are still future work.

## 24. Security and access roadmap

The current application does not implement authentication, authorization, or tenant isolation. Its CORS setting restricts permitted browser origins, but CORS is not an access control system for the API. A command line client can still call an exposed endpoint. This is why demonstration data is appropriate for an assessment deployment and real fleet data should wait for a security layer.
A first improvement would introduce authenticated users and scope fences, vehicles, rules, and history to a tenant. Database queries and WebSocket subscriptions would need the same ownership checks. It would not be enough to protect only the dashboard page while leaving API routes and live messages unrestricted.
Additional work includes rate limits, validation budgets, request deadlines, structured logs, secrets management, audit trails, and secure operational defaults. A rough estimate for a basic authentication and tenancy pass is one to two focused days, followed by review and tests. That estimate depends on identity provider choices and is not a guarantee. It is more useful to name the missing controls and testable acceptance criteria than to call a demonstration application production ready because it has HTTPS and runs inside a container.

## 25. Spatial performance and scale

The current location update checks every fence. If there are many vehicles, many updates per second, and many polygons, this work grows quickly. A mutex that orders all requests also limits throughput. These choices simplify correctness for the assessment, but they should be replaced deliberately when scale requirements justify the complexity.
PostGIS is a natural next step. Store polygons and points in an appropriate spatial reference, add a GiST index, and query candidate containing polygons using a documented boundary policy. The difference between contains and covers matters for points on an edge. Coordinate order also matters when translating the API's latitude longitude pairs into spatial geometry.
Concurrency should be ordered per vehicle rather than by a single global application lock. A transaction can lock the relevant vehicle state while independent vehicles update concurrently. The exact approach must be tested with multiple application instances, because an in memory mutex cannot coordinate separate processes. A reasonable first performance phase is two to three days for schema changes, spatial queries, indexes, migrations, and targeted load tests. Results should be measured with realistic fence complexity and update patterns instead of assuming a spatial index solves every bottleneck.

## 26. Reliable delivery and operational roadmap

The database and live notification stream currently have a small reliability gap: committing an event and sending it are separate steps. A process can stop after the commit and before every client receives the message. The correct next design is an outbox record committed with the location and event. A dispatcher then sends pending messages and records progress with retry behavior.
A broker can distribute events across multiple application instances. Consumers should be idempotent, and the frontend can deduplicate by event identifier. Exactly once delivery is not a useful blanket promise: duplicates, reconnects, acknowledgments, and replay boundaries all need explicit semantics. The persistent history remains the source for recovery and reconciliation.
Operational work also includes readiness checks, graceful shutdown, database backups, retention rules, metrics for update latency and dropped clients, and alerts for service health. A basic outbox and broker phase might take two to three days, with another one or two days for load and failure testing. The important part is to demonstrate failures deliberately: disconnect a browser, restart a process after a commit, slow a consumer, and confirm how records and notifications recover. That produces stronger evidence than testing only a smooth happy path.
